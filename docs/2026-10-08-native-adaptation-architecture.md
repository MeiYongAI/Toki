# 首次适配架构与验证

## 启动流程

1. 对基础包及全部 Split 的 DEX 头、CRC、长度、代码分组计算代码身份。资源 Split 不影响身份，任何新增代码 Split 均参与身份。
2. 本地结果经过 `HostScanPlan` 的代码与规则校验后直接注册。
3. 本地结果不覆盖所需目标时，按完整代码身份读取模块内置适配。校验格式、规则摘要、覆盖范围、成功／失败互斥和完整键值摘要后，在当前启动直接注册；不启动查找线程、不要求重启。
4. 未收录的代码集合通过 DexKit 2.0.7 原生查询获取候选。候选交给同一个 `HostDexIndex` 校验器验证全部成员、指令语义、调用关系、链接指纹和唯一性。
5. 未知构建扫描完成后原子保存并核对，提示手动重启。原生加载或查询失败明确报告，不切换到全量 Java 扫描。

原生库只在确实需要扫描时加载。模块内置结果不是按版本号、地区、包来源选择；同一版本的不同代码集合分别生成结果。

## 候选完备性

- 方法规则按符号选一个入口角色，保留该角色的全部替代规则。一个有效完整契约必然包含入口角色；其余角色继续在候选类内精确验证。
- 原生匹配参数顺序、非混淆类型、精确字符串、明确调用、字段引用、方法名、所属类及必要操作码。混淆通配符在候选阶段放宽，最终仍执行原规则。
- 类指纹由离线生成器同时导出字段数量、方法数量和方法名作为必要条件，完整 SHA-256 结构／语义／链接指纹仍必须全部匹配。
- 倍速和评论各自保留全部可能参与关系的类，跨类关系由统一校验器解析。
- 方法、类指纹、倍速、评论四组候选各自校验，避免通用候选引起不相关的指令遍历。
- 空候选集合表示未匹配，不代表启动全量搜索。多候选不取第一个。

规则目录中没有任何功能引用的 PINCH 已移除；当前 37 个枚举目标均有实际功能依赖。

## 可复现工具

`scripts/GenerateHostProfile.java` 使用同一 Java 校验器离线扫描完整 APK 集合；不依赖版本号，不加载或执行宿主类。参数：资源目录、扫描格式、基础包及全部代码 Split。编译时加入本项目四个 Java 索引类、`HostProfileManifest`、dexlib2 和 Guava。

示例主类参数：

```text
GenerateHostProfile app/src/main/resources index-v9 base.apk split_df_a_dex.apk [全部其他代码 Split]
```

发布前运行单元测试，检查每个规则结构都有原生必要条件、每个清单的规则和格式一致。新增规则或调整成员契约需要重新生成受影响清单。

`scripts/NativeParityRunner.java` 在独立 Android `app_process` 中执行，没有 TikTok 类加载、Hook 安装、视频操作或应用重启。参数为设备 APK 路径列表文件。先计时代码身份计算和内置清单校验，再故意强制原生扫描全部规则，与内置的完整离线扫描结果逐键比较；任何差异直接失败。

这些是独立进程单次样本，不是 TikTok 启动耗时，也不包含 LSPosed 注入和各业务 Hook 注册。文件系统缓存状态未控制。内置构建正常启动不执行表中的强制扫描。

未知构建仍需扫描约 19～21 秒，不能宣称任意新版本即时适配。内置构建的首次扫描已移到发布准备阶段，用户首次启动只做身份与清单验证。继续压缩未知构建时间需要减少全代码原生查询和候选验证读取；不能用延迟提示或减少契约验证替代。

当前实现仍使用 dexlib2 验证候选，原生引擎负责全代码检索；不是将全部验证算法改写为 C++。首轮内置清单已覆盖当前设备代码集合，但尚未安装到宿主验证实际 LSPosed 注册。
